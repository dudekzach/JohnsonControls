Outbound Demo — Build Runbook

Scene A from the demo strategy: agentless notification before a test window expires. Ordered configuration steps for an SC-owned Genesys Cloud org, with the talk track mapped to what you will have built. This revision adds two build steps for a flow that is already live: wiring the contact variables into the TTS actions (Step 4), and a second, purpose-built outbound flow for Answering Machine detection (Step 5).

Read This Before You Start

Three things that will break the demo if you find them out on the day.

1. Every phone number in the JCI mock data is a 555 reserved number

All the workbook numbers are in the 555-01xx fictitious range. An agentless campaign places real calls. If you import those as the dial column, the campaign will attempt, fail, and disposition every record as unreachable — and you will be debugging pacing when the problem is the data.

The generated contact list therefore carries Work_Phone = REPLACE_WITH_YOUR_TEST_NUMBER as the dial column, and keeps the JCI number in Reference_Phone as a display-only field. Substitute two or three numbers you actually control — your mobile, a softphone, a colleague who has agreed to answer — before import. Duplicating the same number across several records is fine and makes the dry run faster.

2. Agentless requires a Call Analysis Response Set containing a Transfer to Flow action

Genesys will reject a response set that transfers to agents, and it will equally reject one that has no Transfer to Flow action, because agentless depends on that action. Build the outbound flow before the response set, and the response set before the campaign. The order below is not arbitrary.

3. An Architect outbound flow cannot be created without a contact list and a default wrap-up code

Both must already exist. So the real build order is: wrap-up codes → contact list → outbound flow → call analysis response set → campaign. Steps 1 through 6 follow that sequence.

Permissions to confirm on your account first

  • Outbound > Campaign > Add, Delete, Edit, Search
  • Outbound > Contactlist > Search · Outbound > Responseset > View

Step 3. Architect Outbound Flow

The notification itself. This is where most of the build time goes.

Architect > Flows > Outbound Call > Add — name it JCI Test Expiry Notification. You will be asked for a contact list (use Step 2's) and a default wrap-up code (use JCI — Message Left).

Outbound flows expose call.contact.<column> derived from the default contact list, so your CSV columns are available directly. Note that some Toolbox actions available in inbound flows are not present here.

Voice and persona

Match the POC: male, professional, business-like, reassuring. Do not use a cheerful assistant voice — this is a life-safety notification and the register carries meaning. Set the TTS voice at flow level so it is consistent across every prompt. verify which male voices are available in your org and pick the same family the POC build uses, so the two demos sound like one product.

If outcomes are unavailable, the reporting beat in Step 9 relies on wrap-up codes and campaign metrics alone, which is still sufficient.

Read this before you paste any of the six scripts below

The {{Site_Name}}-style tokens in these scripts are a documentation convention, not Architect syntax. They mark where a live value has to be wired in — they are not text to type into a Play Message action. If that literal brace text was typed directly into the flow, Architect either read the characters aloud or the field is sitting there as dead static text with nothing driving it, which is the exact symptom this build is now fixing.

Use the wording below to write the literal parts of each script. The actual wiring — replacing each token with a live reference to the contact record — happens in Step 4, once this flow is otherwise built and published.

That test is scheduled to end at {{Test_End_Local}}. If work is still in progress, the system will return to normal alarm handling when the test ends."

This is now a live-call scenario only — a person answered, the menu played, and nobody pressed anything twice in a row. It is not the message a machine hears. Once Step 5 is built, Answering Machine results never reach this flow at all; they are routed by the response set straight to a dedicated flow with its own one-way message.

Do-not-contact confirmation

TTS

"This number has been removed from automated notifications. Thank you."

Two deliberate choices worth defending in the room

The notification never states a PIC, and never asks for one. It confirms a site and offers an action. Consistent with the inbound design, an authorisation decision does not happen over an unauthenticated outbound call.

Press 9 exists. A self-service opt-out that permanently marks the contact uncallable is the strongest single answer to a compliance question, and it costs one menu branch.

Publish the flow. It must be published before the response set can reference it — but publishing only makes the literal wording live. The braced tokens are still just text at this point. Step 4 replaces them with real per-contact values.

Step 4. Wire the Contact Variables into the Prompts

The six scripts in Step 3 are the words. This step makes four of them true for each contact record.

A Play Message action in Architect does not hold a single text field with placeholders inside it. It holds an Audio Sequence — an ordered list of small cards that play back to back. Some cards are literal spoken text. Some cards are data. Wiring a variable into a prompt means editing that sequence, not editing text inside a box.

How the Edit Audio Sequence dialog works

  1. Open the flow, and open the Play Message (or equivalent Communication) action carrying the prompt you want to wire.
  2. Click into its Text-to-Speech content. This opens the Edit Audio Sequence dialog.
  3. The dialog holds an ordered list of sequence cards. Add TTS adds a literal spoken-text card — type the wording exactly as it should be read. Add Data adds a variable card, with a Select Options control that decides how the value is rendered — Text to speech for a plain string, or a date- or number-specific rendering if the underlying variable is a typed Date or Decimal rather than a String.
  4. Build each message by alternating cards: a TTS card for every literal chunk of wording, a Data card wherever a {{...}} token sat in the script in Step 3.

The variable path

Every column in the contact list attached to this flow is exposed as call.contact.<ColumnName> — confirmed directly against Genesys's own documentation for outbound flows, not carried over from memory. It's case-sensitive; use the exact header spelled out in Step 2's column table: Site_Name, Site_Address, Test_End_Local, Max_Duration_Hours.

verify In the Data card, browse the variable picker to the contact object rather than typing the reference blind — confirm the exact capitalization Architect shows you for your org's build. It should resolve to something like Call.Contact.Site_Name.

Worked example — the Greeting

The Step 3 script reads: "This call concerns the system test currently active at {{Site_Name}}, {{Site_Address}}. That test is scheduled to end at {{Test_End_Local}}." As a sequence of cards:

1. TTS   "This is an automated notification from Johnson Controls
          monitoring. This call concerns the system test currently
          active at "
2. Data   call.contact.Site_Name           → Select Options: Text to speech
3. TTS   ", "

5. TTS   ". That test is scheduled to end at "
6. Data   call.contact.Test_End_Local      → Select Options: Text to speech

Menu and the Do-not-contact confirmation have no {{...}} tokens in Step 3's scripts — leave them as pure TTS cards. Nothing to wire.

Check what Test_End_Local actually contains before you wire it

If the column holds a friendly, already-localised string per site — for example 2:00 PM — a plain Text to speech card reads it naturally and you're done. If it holds a raw ISO timestamp instead — for example 2026-09-11T14:00 — a plain Text to speech card will read the characters, not a time, and it will sound broken on the call. Open the contact list and check a real record before you wire this one. If it's the raw form, either reformat the source CSV to a spoken-friendly string, or use a Date/Time-aware Select Options entry on the Data card so it renders as a time instead of literal digits.

verify Max_Duration_Hours is a plain number of hours (e.g. 8) — Text to speech should read it correctly, but confirm the rendered audio in the debug session below rather than assuming it does.

Verify before moving on

  • Use Architect's Test/Debug tool to run a text-based session against a real contact record.
  • For each of the four wired prompts, confirm the resolved output shows the actual per-contact value — not blank audio, not a validation error, and not the literal {{...}} characters.
  • Republish. A save alone does not change what a running or future campaign dial actually plays — only a new published version does.

Step 5. Second Outbound Flow — Answering Machine Message

One flow, one job: leave a clean one-way message and disconnect. No menu — a machine cannot press a key.

Today, Answering Machine results transfer into the same flow as Live Voice, which means a machine sits through the full interactive menu it can never respond to, and only reaches a message after two silent retries time out. A second, purpose-built flow is the correct pattern here, not a workaround — confirmed directly against Genesys's own documentation: Live Voice and Answering Machine each pick their own action independently in the response set, including their own Transfer to Outbound Flow target. There is no reason to make a machine wait through a menu it cannot use.

Build it

  1. Architect > Flows > Outbound Call > Add — name it JCI Test Expiry Notification — Machine Message.
  2. Contact list: the same JCI Test Expiry Notification list from Step 2. A flow needs a contact list to be created at all — it does not need to be a different one from the live flow's.
  3. Default wrap-up code: JCI — Message Left, same as the live flow. Either disposition path lands here; it's non-mapped so attempt controls can still recall if you want that.
  4. Voice and persona: the same TTS voice family as the live flow, set at flow level, so the two flows sound like one product rather than two different builds.

Flow structure

Start
 └─ Set Participant Data          site=call.contact.Site_Name, cs=call.contact.CS_Number,
                                  ends=call.contact.Test_End_Local, notify_type="test-expiry-machine"
 └─ Play Message  (TTS)           one-way voicemail message — no menu, no input collection
 └─ Set Wrap-up "JCI — Message Left"
 └─ Disconnect
Why Set Participant Data still matters with no agent on the call

It keeps this flow's interaction record structured the same way the live flow's is, so the Campaign Interaction Detail view in Step 9 shows a consistent shape whether a given attempt landed on a live answer or a machine — which is exactly the comparison worth showing live.

Prompt text — copy directly, then wire like Step 4

TTS

"You have reached an automated notification from Johnson Controls monitoring. This message concerns the system test currently active at {{Site_Name}}. That test is scheduled to end at {{Test_End_Local}}. If the test needs to be extended, please contact the central station directly. No action is required if the test can end as scheduled. This message will now end."

Deliberately different register from the live flow's timeout close: this is one-way, so it front-loads the callback instruction rather than offering an action the listener cannot take. Wire Site_Name and Test_End_Local into this one Play Message action using the exact Add TTS / Add Data method from Step 4 — same variable path, same Select Options choice, same debug-session check before you move on.

verify Call Analysis Responses also expose a separate Answering Machine Timeout setting — the action taken if beep/greeting-end detection itself times out before AMD can classify the call. It offers the same three choices (Hang up, Transfer to queue, Transfer to Outbound Flow). Point it at this same flow if your org's response-set editor surfaces it, so a borderline detection doesn't fall back to the live-voice flow by default.

Publish the flow. It must be published before Step 6's response set can list it as a transfer target.

Do not carry the pacing warning across from the wrong context

Genesys documentation warns against transferring live voices to Architect flows because the flow answers everything immediately and destroys the pacing algorithm. That warning applies to agent-paced modes — progressive, power, predictive. Agentless has no agent pacing to disrupt, and Transfer to Flow is the intended mechanism. Worth knowing precisely, because if someone in the room has read that article you want to be able to explain the distinction rather than look caught out.

Step 7. Compliance Objects

Build these even though the campaign will run without them. They are the first thing you show.

Contactable time set

Admin > Outbound > Contactable Time Sets > Create New — JCI Notification Window.

  • Add an entry per time zone present in the list: America/New_York, America/Chicago, America/Denver, America/Los_Angeles.
  • Set each to a defensible window — 08:00 to 20:00 local, Monday to Saturday.
  • The campaign will refuse to save with a contactable time set assigned unless the contact list has a timezone column. Yours does.
Demo-day trap

If your session runs at 07:30 Mountain and the window opens at 08:00, the campaign will correctly dial nothing and you will look broken. Either widen the window for the demo, or — better — leave it as configured and use it as the point: "it's not dialling, and that's the control working." Then widen it live to prove the campaign responds. Decide which before you present, and rehearse it.

Attempt controls

Admin > Outbound > Attempt Controls. Cap attempts per contact and per number, and set a recall interval for busy, no answer, and machine outcomes. Modest values — two attempts, thirty minutes apart — keep the demo tidy.

Rule set optional

Admin > Outbound > Rule Management — JCI Notification Rules. One useful pre-call rule: skip records where Hours_Remaining is greater than 24, so only imminent expiries are dialled. This is a better demonstration than a contact list filter because it shows automation deciding, and it visibly excludes JCI-012 at 26 hours.

Step 9. Pre-build the Reporting

The closing beat fails if you are configuring a view live with an empty result set.

  • Run the campaign at least twice before the session so historical views have data. An empty Campaign Performance view is a worse ending than no ending.
  • Save a filtered Campaign Performance Summary view — dials, contacts, connect rate, abandon measures, campaign progress.
  • Save a Campaign Interaction Detail view so you can drill into a single attempt and show the wrap-up code that resulted.
  • If Flow Outcomes are available in outbound flows, save a Flow Outcome Performance view for Notification Accepted. verify
  • Dial at least one test record against a real voicemail box you control, not just a live answer, so Campaign Interaction Detail shows an attempt that resolved through the machine-message flow, distinct in shape from one that resolved through the live flow.
  • Have the inbound Test-On reporting open in an adjacent tab. The closing line depends on both being visible in the same analytics framework — that comparison is the whole point of the beat.
